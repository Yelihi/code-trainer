# 학습 지식 그래프 전환 계획

## 2026-10-20 배포 범위

- `관계 → 지식 그래프`의 탐색 화면과 오른쪽 상세 패널을 구현했다.
- 현재 지도에는 **학습자가 ‘개념 지도에 추가하기’로 명시적으로 등록한 단원**을 넣는다. 생성·열람·문제 통과만으로 등록하지 않는다. 자료 학습과 기초 학습 모두 문제 없이 추가할 수 있다.
- `knowledge_entries`는 사용자·노드별 최초 등록 시각, 출처/단원/버전과 학습 내용 스냅샷을 저장한다. 원본 삭제 후에도 스냅샷은 보존한다. 이후의 통과 문제는 등록한 단원의 별도 근거로 연결한다. 기존 날짜별 `learning_records`는 유지한다.
- 현 단계의 개념 목록은 출처 단원 안에서 구분한다. 이름이 같다고 다른 출처의 개념을 자동 통합하지 않는다. 아래의 정식 개념 ID·주장·온톨로지 이관 및 GraphRAG는 후속 설계이며, 이번 배포가 이를 완료한 것은 아니다.

## 결정

포스팅 기반 과정과 자료구조·알고리즘 과정이 **같은 개념 ID**를 참조하게 한다. 개념의 내용, 개념 사이의 관계, 학습자의 수행 기록을 별개로 저장한다. AI는 새 개념·관계의 후보를 제안하고, 검증된 근거만 그래프와 복습 문서에 사용한다. 그래프는 현재 SQLite에 관계형 테이블로 저장한다. 그래프 데이터베이스나 RDF 엔진은 이 단계에 필요하지 않다.

```
포스팅 ─┐
       ├→ 출처 → 근거가 있는 주장 → 개념 ← 관계 → 개념
기초 단원 ┘                         ↑
                              학습 관찰 ← 통과·복습 제출
                                   ↓
                         학습 상태·복습 문서(파생 결과)
```

이 그림에서 **출처**, **개념**, **주장**, **학습 관찰**은 서로 다른 것이다. 포스팅에 등장했다는 이유로 학습 완료가 되지 않고, 문제 하나를 통과했다는 이유로 해당 단원의 모든 개념을 숙달한 것으로 기록하지 않는다.

## 현재 코드에서 바뀌어야 할 경계

- `backend/learning.py`는 첫 통과 제출과 기초 구현의 통과 기록을 모아, 전체를 한 번에 AI로 요약한다. `root_key`가 언어 또는 프레임워크여서 두 경로의 동일 개념이 별개가 될 수 있다. 결과는 `(root_key, 이름)` 단위로만 합쳐지고 개념 간 관계가 없다. 입력 240 KB 제한도 있다.
- `backend/service.py`의 `learning_map()`은 단원에서 생성된 개념 문자열로 트리를 만들고, 초안과 통과를 단원별로 표시한다. 이 화면은 그래프 전환 뒤에도 이전 기록 조회용으로 잠시 유지할 수 있지만 새로운 지식의 정본은 아니다.
- `backend/foundation_catalog.py`의 단원 ID와 `prerequisites`는 사람이 작성한 좋은 초기 개념 및 선행 관계 후보이다. 선행 단원과 선행 **개념**은 별도로 확인해야 한다.
- `backend/db.py`의 `learning_records`는 날짜별 불변 요약이다. 이 기록은 이관 과정에서도 날짜·내용·삭제 표시를 유지한다. `frontend/src/LearningMap.tsx`와 `frontend/src/api.ts`는 새 그래프 API를 읽도록 단계적으로 바꾼다.
- `backend/service.py`의 자료 삭제는 원문과 풀이를 삭제하지만 과거 학습 요약은 보존한다. 새 그래프도 출처 삭제 뒤 남는 근거와 화면 표시를 명시해야 한다.

## 최소 온톨로지

| 대상 | 저장할 핵심 정보 | 규칙 |
| --- | --- | --- |
| 개념 `Concept` | 변경되지 않는 ID, 대표 이름, 짧은 정의, 범위, 상태 | 이름이나 포스팅 ID를 식별자로 쓰지 않는다. `큐`와 `JavaScript 배열 기반 큐 구현`은 범위가 다르므로 별개일 수 있다. |
| 별칭 `Alias` | 표기, 언어, 연결된 개념 ID | 같은 뜻으로 확인된 표기만 별칭이다. 유사한 단어라는 이유만으로 합치지 않는다. |
| 주장 `Claim` | 주어 개념, 서술문, 적용 조건, 유효 상태 | `큐는 FIFO다`와 `head 인덱스 구현은 매번 shift하지 않는다`를 별개 주장으로 둔다. 출처마다 충돌하면 덮어쓰지 않는다. |
| 관계 `Edge` | 시작 개념, 관계 종류, 끝 개념, 적용 범위, 상태 | `PREREQUISITE_OF`, `BROADER_THAN`, `USED_IN`, `RELATED_TO`부터 시작한다. 앞의 세 관계는 방향을 지킨다. `RELATED_TO`는 대칭 관계로 정규화한다. |
| 근거 `Evidence` | 주장 또는 관계 ID, 출처 종류·ID·버전, 문단/단원/제출 위치, 지지·반박, 생성 시각 | 출처를 실제로 찾을 수 있어야 한다. AI의 답변 자체는 원문 근거가 아니다. |
| 학습 관찰 `LearningObservation` | 학습자, 개념 ID, 제출·복습 ID, 실제 수행 종류, 도움 사용, 시각 | READ·FIX·MODIFY·BUILD·기초 구현과 복습을 구분한다. `숙달`은 관찰에서 계산한 화면 상태일 뿐 영구 사실로 쓰지 않는다. |

언어·프레임워크·자료구조 같은 분류는 개념의 **관점/태그**다. 트리의 루트가 아니다. 한 개념이 여러 분류, 여러 포스팅, 여러 학습 과정에 속할 수 있다. 안정된 개념 ID를 사용하면 이름 변경과 분류 변경에도 연결이 유지된다. 개념을 합칠 때는 기존 ID를 바로 삭제하지 않고 별칭·이관 기록으로 참조를 유지한다.

관계의 의미를 먼저 고정한다. `A PREREQUISITE_OF B`는 B를 학습하기 전에 A가 필요하다는 교육적 판단, `A BROADER_THAN B`는 B가 A의 더 좁은 개념, `A USED_IN B`는 B에서 A를 실제로 사용한다는 뜻이다. 예를 들어 `큐 USED_IN BFS`는 타당할 수 있지만, 같은 글에서 함께 언급된 것만으로 성립하지 않는다. `BROADER_THAN`에는 순환을 허용하지 않는다. 선행 관계의 순환도 검토 대상으로 보낸다. 범위가 다르거나 반례가 있으면 `RELATED_TO`로 뭉개지 않고 별개 후보로 남긴다. 여기서 `검증됨`은 근거 위치와 의미를 확인했다는 뜻이며, 모든 상황에서 절대적으로 참이라는 뜻이 아니다.

이 분리는 [SKOS의 대표명·별칭·상하/연관 관계](https://www.w3.org/TR/skos-reference/)와 [PROV-O의 출처 추적](https://www.w3.org/TR/prov-o/)에서 설계 원칙을 가져온 것이다. 표준 전체를 구현할 필요는 없다. 타입·필수 필드·참조·관계 방향을 검증하는 규칙은 [SHACL의 그래프 검증 개념](https://www.w3.org/TR/shacl/)에 대응시키되 처음에는 SQLite 제약과 애플리케이션 검증으로 구현한다.

## 저장 구조와 불변 조건

현재 규모에서는 소유자별 SQLite 테이블이면 충분하다. 제안 테이블은 `knowledge_concepts`, `knowledge_aliases`, `knowledge_assertions`(주장 또는 방향 관계), `knowledge_sources`, `knowledge_evidence`, `learning_observations`다. 모든 사용자 데이터에는 `owner`가 들어가고, 외래 키와 조회 조건에 소유자를 함께 묶는다. 관계형 저장이어도 인접 노드 조회와 1~2단계 탐색을 할 수 있다. 실제 탐색량·지연이 문제가 될 때 저장소를 재평가한다.

`knowledge_assertions`는 주어 개념 ID와 `kind`를 가진다. 주장이면 검증 가능한 문장과 적용 범위가, 관계면 목적어 개념 ID와 허용된 관계 종류가 필수다. `knowledge_evidence`는 하나의 주장/관계에 여러 출처를 연결한다. 출처에는 등록된 글/원문, 생성된 단원 버전, 기초 카탈로그 버전, 제출 또는 복습 ID를 기록한다. 출처가 있는 **주장**과 학습자가 수행한 **관찰**은 별도 조회한다. 생성 문서는 별도 산출물로 두고 사용한 주장·관계·출처 ID 및 그래프 버전을 기록한다.

저장 전에 다음을 검사한다.

1. 양 끝 개념이 같은 소유자의 유효한 ID인지, 자기 자신을 가리키는 관계인지 확인한다.
2. 근거의 출처가 존재하고 요청자가 볼 권한이 있는지 확인한다. 근거 없는 AI 제안은 `candidate`에서 멈춘다.
3. 중복 별칭, 중복 관계, 상하 관계 순환, 선행 관계 방향 오류, 상반된 주장·출처 변경을 검토 대상으로 분류한다.
4. 같은 이벤트를 재처리해도 개념·관찰이 중복 생성되지 않도록 출처 ID+버전+위치와 제출 ID에 고유 제약을 둔다.
5. 기존 원문 접근 정책을 지킨다. 그래프 API에는 관리 전용 원문이나 제출 코드를 복제하지 않는다.

## 두 입력 경로의 공통 처리

1. **출처 고정:** 포스팅 등록 시 URL, 가져온 시각, 콘텐츠 해시, 문단/제목 위치를 남긴다. 기초 과정은 단원 ID와 버전을 쓴다. 이미 있는 `source_documents`와 카탈로그를 재사용한다.
2. **작은 단위 추출:** AI는 출처에서 개념 후보, 짧은 원자적 주장, 관계 후보, 각 후보의 정확한 근거 위치와 적용 범위를 구조화해 제안한다. 생성된 설명글을 원문 근거로 재사용하지 않는다.
3. **개념 연결:** 기존 ID/별칭 일치 → 정의·적용 범위 비교 → 의미상 가까운 후보 검색 → `동일 / 더 구체적 / 관련 / 별개 / 판단 보류` 판정 순서로 처리한다. `React의 상태`와 일반 `상태`처럼 이름이 같아도 뜻이 다를 수 있고, 이름이 달라도 같은 개념일 수 있다. 처음에는 현재 소유자의 후보와 기초 카탈로그만 검색하고, 임베딩은 실제 누락률이 높을 때 추가한다.
4. **승인 및 기록:** 코드로 확정 가능한 카탈로그 연결은 검증 후 반영한다. AI만 제안한 병합·방향 관계, 충돌하는 주장은 후보로 두고 사람이 근거 문장을 보며 승인·거절·수정할 수 있게 한다. 승인 이력과 모델/프롬프트 버전을 보관한다. [LLM 기반 그래프 구축 연구](https://arxiv.org/abs/2403.08345)도 자동 생성 결과를 사람이 평가하는 접근을 권한다.
5. **학습 연결:** 글/기초 단원은 가르치는 개념 ID를 참조한다. 제출이 통과하면 그 문제의 실제 요구사항에 대응하는 개념과 수행 유형만 `LearningObservation`으로 남긴다. 힌트·정답 열람과 복습 결과를 함께 반영한다. 원문에 없는 능력을 학습 완료로 추정하지 않는다.

이 순서라면 두 번째 포스팅이 같은 주제를 다뤄도 새 개념을 무조건 만들지 않는다. 기존 개념에 새로운 주장·사례·반례·출처를 추가할 수 있다. 더 좁은 주제라면 새 개념을 만들고 방향 관계로 연결한다.

## 활용 방식

- **학습 화면:** `관계 → 지식 그래프` 메뉴에서 전체 노드와 연결을 먼저 보여 준다. 드래그 이동, 확대·축소, 전체 보기, 검색을 제공한다. 노드 hover와 키보드 포커스에서 연결 노드·선을 강조하고 나머지는 흐리게 한다. 클릭하면 오른쪽 drawer에 개념 설명, 관계의 종류·방향·근거, 이전에 풀었던 복습 문제를 보여 준다. 모바일에서도 패널을 열고 닫을 수 있고 키보드와 모션 감소 설정을 지원한다. 관계 목록 보기와 날짜별 `learning_records` 선택도 제공한다.
- **복습 문서:** 목표 개념 또는 연결된 2~3개 개념을 선택 → 검증된 주장과 근거가 있는 관계만 탐색 → 겹치는 설명을 합치고 서로 다른 조건·반례를 남김 → 출처와 연습 문제 링크가 달린 초안 생성 → 문장마다 사용한 주장 ID를 검증 → 사용자 검토 후 저장한다. 문서는 정본이 아니며 원 주장이나 출처가 바뀌면 재검토 표시를 한다. 그래프를 통해 관련 내용을 모아 요약하는 방향은 [Microsoft Research의 GraphRAG 연구](https://www.microsoft.com/en-us/research/publication/from-local-to-global-a-graph-rag-approach-to-query-focused-summarization/)와 닿지만, 이 앱에서는 먼저 작은 근거 그래프와 사용자 검토에 집중한다.
- **FS 재사용:** FS가 Frontend System을 뜻한다면 데이터 계약을 그대로 적용한다. `개념 = 접근성/상태 관리/배포 패턴`, `출처 = 코드·문서·검사`, `주장 = 이 코드가 따르는 구체적 규칙`, `관계 = 선행/적용/연관`, `관찰 = 실제 테스트·리뷰 결과`다. 학습 앱의 `READ/FIX` 같은 수행 유형은 FS에 이식하지 않고 도메인별 관찰 유형으로 바꾼다.

## 이행 순서와 완료 기준

1. **기준 자료 만들기:** 기존 학습 기록과 기초 단원, 서로 비슷한 포스팅을 대상으로 동일·부분 중복·다른 의미·상충·선행 관계 사례를 약 40~50건 사람이 판정한다. 두 경로가 같은 개념을 가리키는 사례를 반드시 넣는다.
2. **저장과 이관:** 백업 및 롤백 절차를 마련하고 새 테이블·제약을 추가한다. 기초 단원 ID는 초기 후보로 적재한다. 과거 `learning_records`는 수정하지 않는다. 과거 요약의 개념명은 자동 확정하지 않고 이관 후보로 연결한다. 원본 삭제 이력이 있는 근거는 없는 출처를 꾸며내지 않는다.
3. **증분 그래프 생성:** 새 포스팅, 단원 버전 변경, 통과 제출, 복습 완료에서 해당 출처/관찰만 처리한다. 기존의 전체 재요약 240 KB 경로를 새 그래프의 정본으로 사용하지 않는다. 실패·재시도·중복 이벤트에서 결과가 안정적인지 확인한다.
4. **조회와 검토 UI:** 개념 중심 조회, 관계 방향·근거 표시, 후보 승인·거절, 기존 날짜별 기록 링크를 추가한다. 연결된 개념의 자료를 삭제했을 때 출처 상태와 재검토 표시를 확인한다.
5. **복습 문서:** 검증된 그래프에서만 초안을 만들고 문장별 근거를 검사한다. 생성된 문서는 그래프에 새 사실로 자동 재투입하지 않는다.

승인 기준은 **없는 출처를 인용한 주장 0건, 다른 사용자의 자료 노출 0건, 재처리 중복 0건, 기존 날짜별 기록 손상 0건**이다. 기준 자료에서 잘못된 자동 병합·관계 방향 오류가 나오면 해당 종류의 자동 확정은 끄고 검토 후보로만 남긴다. 개념별 조회와 2단계 탐색의 지연, 후보 검토량, AI 비용은 실제 데이터로 측정해 다음 확장 여부를 결정한다.

자료 삭제 시 현재처럼 원문·풀이의 삭제와 과거 학습 기록의 보존을 분리한다. 삭제된 출처만 지지하던 주장/관계는 활성 그래프에서 내리고 과거 스냅샷에는 `출처 삭제됨`으로 남긴다. 다른 유효 출처가 있으면 그 근거로 유지한다. 전체 학습 기록까지 지우는 기능이 필요하면 별도 삭제 정책과 UX를 정의한다.

## 현재 구현 범위 (2026-10-20)

그래프 탐색 화면과 `/api/me/knowledge-graph` 읽기 API를 먼저 구현했다. 현재 SQLite의 학습 요약·통과 기록을 그래프로 변환한다. 개념 → 통과한 학습 단원은 `학습 근거`, 같은 버전의 기초 카탈로그에서 확인한 단원 → 단원은 `선행 단원`으로 명확하게 구분한다. 현재 보기에는 새 통과 단원을 포함하고 날짜별 보기에는 선택한 기록의 근거만 포함한다. 삭제된 근거는 역사 기록으로 표시하며 문제 링크를 제거한다.

이 단계는 화면과 기존 근거 데이터의 연결이다. 위 계획의 영구 개념 ID, 의미 기반 중복 통합, 원문 문단별 주장 추출, 승인 이력 및 파생 복습 문서 생성은 아직 구현하지 않았다. 현재 개념 ID는 기존 요약의 분류와 이름에서 결정적으로 계산하므로, 이름을 바꾸거나 의미를 통합할 때는 정식 개념 ID로 이관해야 한다.
