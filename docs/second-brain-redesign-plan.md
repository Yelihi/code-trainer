# 레퍼런스에서 세컨드 브레인으로 — 개편 설계 초안

작성: 2026-10-22 · 상태: 최초 설계의 역사 기록

2026-10-25 후속 구현과 확정된 정책은 [release 테스트·유지보수 안내](release-testing.md), [release 완결 작업](release-completion-plan.md) 및 흐름별 구현 계획을 따른다. 아래의 ‘미착수/미확정/도구 미노출’ 표현은 작성 당시 상태다.

## 1. 목표와 이번 작업의 경계

> 복잡한 세상의 수많은 레퍼런스를 저장하고, 인간이 이해하고, 세컨드 브레인을 강화하며(그래프), 강화된 브레인은 창조의 기반이 된다. 집중되는 초점은 컴퓨터와 개발이다.

제품의 기본 단위를 **문제 생성 요청**에서 **보관된 자료**로 바꾼다. 원문 등록, AI 해석, 사용자 학습, 지식 등록, 응용 제안은 각각 독립적으로 저장·조회·재시도할 수 있어야 한다. 자료를 저장하기 위해 실행 언어나 난이도를 고르거나 AI를 호출할 필요가 없어야 한다.

이번 산출물은 현재 코드에 근거한 개편 계획이다. 제품·테스트·DB·운영 설정은 수정하지 않는다. 아래 사용자 요구와 구현 제안을 구분하며, 제안을 구현 승인으로 간주하지 않는다.

- 작업 브랜치: `plan/second-brain-redesign`
- 분기 기준: 기존 작업 브랜치 `fix/reference-quote-repair`의 `396b48d85d36fd14f8786ae7a771252b6f4abe4b`. 최근 노트 검토·인용 보정 기능을 포함한다.
- 로컬 `main`: `f81c24e773fc635a8f78ef5d3cde416bdf6ca04b`. 현재 작업 코드보다 뒤에 있으므로 이번 관찰을 main의 사실로 기록하지 않는다. 원격 fetch·최신 병합 여부 확인은 하지 않았다.
- 시작 시 존재하던 `PLAN.md` 수정과 미추적 `docs/deployment-design.md`는 보존한다. 이 브랜치의 후속 커밋에 자동 포함하지 않는다.
- FS `get_project_analysis`, `get_work_context`, `save_project_context`, `save_revision` 도구가 이번 세션에 노출되지 않았다. 이 파일은 **FS에 바인딩되지 않은 초안**이며 정식 revision·승인·전체 분석 완료 기록이 아니다. 기존 `.frontend-system/init.md` 등은 역사 기록으로 유지한다.
- 검토 범위: 메뉴/라우트, 등록·생성·삭제, 노트·온톨로지, 코드 복습, 피드, AI/GitHub 설정 및 검사 명령. 전체 159개 추적 파일의 전수 분석이나 런타임 검증을 완료한 것은 아니다.

| 설정 | GitHub 연동 | 계정 연결, 기본 저장소 등록/확인, 공유 기록 | 기존 연결/검사 재사용, 기본 저장소 저장 추가. 외부 게시 동작은 계속 명시적으로 실행 |
| 설정 | AI 연결 | 사용자 키·모델 등록/교체/삭제, 연결 상태·사용량 | 신규 설정 + 기존 사용량 화면 |
| 설정 | 운영 상태 (관리자) | 기존 운영 상태/제보 등 관리 도구 | 관리자 권한 유지 |

`나의 기록`은 탐구하기 화면의 보조 링크로 유지하고, 사용량은 AI 설정에서도 접근한다. 관리자 원문 페이지는 이관 진단 용도로 유지할 수 있지만 자료 등록의 주 진입점은 아니다. 브랜드 변경은 이번 범위 밖이다.

제안 라우트: `/library`, `/library/new/note`, `/library/new/reference`, `/explore`, `/explore/practice`, `/knowledge/candidates`, `/apply`, `/settings/ai`. 기존 `/inbox`, `/reviews`, `/knowledge`, `/settings/github`와 상세 URL은 가능한 한 유지한다. `/create`와 `/references`는 전환 기간 별칭/안내 진입점을 제공하고, `feed_post_id` 등 실제 쿼리와 기존 공유 링크의 식별자를 보존한다. 정확한 별칭 처리는 라우트 구현 흐름에서 모든 호출자를 확인한다.

### 화면 구성 초안

```text
왼쪽: 다섯 영역의 탐색                 본문: 선택한 자료의 현재 작업

자료 보관함   [검색] [종류] [상태]       [+ 노트] [+ 레퍼런스]
제목 / 출처 / 원문 버전 / 해석 현황 / 마지막 수정
자료 상세: 원문 | 해석 기록 | 내 학습 | 연결된 지식
                                         [해석 시작]

해석 상세     출처·버전 / 섹션 목록 / 개념 설명 / 내 이해 메모
             [질문·요약 작성] [코드 문제 생성] [추출 검토로]

추출 상세     왼쪽: 근거 문장·작성자·버전
             오른쪽: 후보 개념·정의·관계·기존 개념 비교
             [수정] [보류] [선택 내용 등록]

Deep Inside  연결 근거 → 생각할 질문 → 참고 자료 → 직접 할 작은 실습
             [채택하여 탐구 시작] [넘기기]
```

최초 로딩, 빈 목록, 처리 중, 실패·재시도, 기존 결과를 보며 재생성 중인 상태를 별도로 표현한다. 저장 실패·세션 만료 시 작성 내용을 유지하고, 모바일 메뉴·키보드·포커스·상태 알림을 기존 접근성 수준 이상으로 보존한다. 이 도식은 제안이며 실행 화면이나 FS 생성 HTML이 아니다. 정식 페이지/scene HTML과 실제 화면 캡처는 P0 분석 후 연결한다.

## 5. 데이터와 상태의 경계

아래 이름은 설계용 논리 이름이다. 물리 테이블의 전체 재명명이나 기존 ID 교체를 요구하지 않는다.

| 데이터 | 소유하는 정보 | 다른 단계와의 연결 |
| --- | --- | --- |
| Raw resource / revision | 원문, 직접 노트, 출처 메타데이터, 수집 결과, 버전·시각·본문 해시 | 해석이 없어도 독립 조회. AI 결과가 원문을 덮어쓰지 않음 |
| Interpretation | 특정 원문 버전을 해석한 개념 문서·섹션·생성 설정·작업 상태 | 하나의 자료에서 새 해석을 만들 수 있으나 기존 결과와 기록을 덮어쓰지 않음 |
| Learning artifact | 질문 답변, 사용자 요약, 코드 풀이/제출, 복습 기록 | 해석/섹션/문제/카탈로그 버전을 참조. AI 예시 답변과 사용자 작성 구분 |
| Extraction candidate | 출처 버전, 검토 상태, 후보 개념·주장·관계, 정확한 근거, 사용자 선택 | 해석과 실습 양쪽에서 같은 검토 경로에 접근 |
| Knowledge | 확정 개념·별칭·주장·관계·근거·학습 관찰 | 기존 ontology 사용. 등록으로 숙달이나 객관적 진실을 자동 선언하지 않음 |
| Application suggestion | 그래프 근거, 질문, 참고 자료, 실습 가이드, 채택 상태 | 채택 시 저장된 탐구가 되고, 사용자 결과물은 다시 raw/학습 자료가 될 수 있음 |

**원문 저장 제안:** 생성 작업에서 독립된 `resources`와 가져온 본문의 `resource_versions`를 추가한다. 기존 노트 본문·이미지·버전은 당장 복제하지 않고 resource가 `reference_notes`와 `reference_note_versions`를 참조한다. 노트 편집의 쓰기 주체는 기존 노트 서비스 하나로 유지한다. URL/텍스트 원문의 쓰기 주체는 새 자료 서비스다. 목록과 상세 API에서 같은 자료 인터페이스로 제공한다. 참조 키에는 소유자·종류·ID·버전을 포함하고 소유권을 검증한다. 별도 범용 저장 프레임워크는 만들지 않는다.

**해석 저장 제안:** 기존 `contexts`와 상세 URL/ID를 활용하되 새 일반 해석 계약을 별도로 정의한다. 기존 코딩 과정은 legacy 형태로 읽을 수 있어야 한다. 새 해석은 원문 버전에 연결된 새 결과로 저장하고, 코드 문제는 특정 해석 결과와 섹션에 연결한다. `LearningUnit.has_example`을 전역 삭제해서 코드 문제 품질 검증까지 완화하지 않는다. 실행 언어·난이도는 코드 문제 요청 시 결정하고, 기존 과정의 설정은 그대로 유지한다. 같은 해석 섹션의 다중 언어 문제 세트는 첫 범위에서 제외하며, 이미 생성된 세트의 언어를 조용히 변경하지 않는다.

상태는 단계별로 독립적이다. ‘그래프 등록됨’이 원문의 유일한 최종 상태가 되어서는 안 된다.

- 원문 수집: `pending → fetching → ready | failed`. URL 가져오기 실패에도 입력 URL과 실패 상태를 남기며 재시도할 수 있다. 보관 여부는 별도 상태다.
- 해석 작업: `queued → running → ready | failed | interrupted`. 재시도는 고정된 원문 버전에 연결된다. 새 버전 도착은 기존 결과를 소급 변경하지 않는다.
- 학습 기록: `draft → saved → reviewed`. reviewed는 사용자의 학습 정리 확인을 뜻하는 제안이며 AI 정답 판정과 다르다.
- 추출: `eligible → proposed → registered | deferred`, 근거 변경 시 `stale`. 적격 자료 목록 진입과 유료 AI 후보 추출은 구별한다. 목록 조회만으로 AI를 호출하지 않는다.
- 응용: 현재 제안 묶음에서 `accepted`만 장기 저장하는 안을 권장한다. 넘긴 제안의 중복 억제에 필요한 최소 식별자와 생성 시각의 보관 기간은 확정이 필요하다.

### 공통 보존 규칙

1. 서버가 인증 사용자로 owner를 정한다. 관리자 원문 API를 일반 사용자에게 그대로 노출하지 않는다. 새 본인 자료 API는 항목별 소유권을 검사한다.
2. AI 해석과 사용자 요약은 각각 해석·사용자 작성 근거로 표시한다. 해석을 인용했다는 이유로 원문이 직접 주장한 사실처럼 표시하지 않는다.
3. 입력 변경 후 늦게 도착한 AI 결과는 요청했던 버전에 붙인다. 최신 문서나 다른 사용자의 화면을 덮어쓰지 않는다.
4. 재전송/중복 클릭은 같은 요청을 재사용하고, 내용이 다른 동일 요청 ID는 충돌로 처리한다. 사용자 확인 후 그래프 등록은 하나의 트랜잭션이다.
5. 보관·삭제·원문 수정 시 관련 근거의 active/stale/deleted 의미를 유지한다. 기존 그래프와 날짜별 학습 기록을 자동 재해석하거나 일괄 합치지 않는다.
6. 소유자의 노트/원문, 이미지, 출처 버전, 코드, 비공개 정답의 공개 범위는 각각 유지한다. GitHub 공유 미리보기에서도 새로운 raw 전체가 암묵적으로 포함되지 않게 한다.

## 6. 단계별 기능 설계

### 등록하기

직접 노트와 레퍼런스는 한 보관함의 입력 종류다. 저장은 AI 키·샌드박스 없이 가능해야 한다. 기존 텍스트/Markdown/URL/지원 파일 범위를 유지하며 PDF·영상 전사·메일 연동은 별도 후속 범위다. URL 수집은 기존 `source.fetch`의 공개 주소·redirect·용량 검사를 재사용한다.

RSA는 기존 RSS/Atom 수집 경로를 기반으로 한다. 대기 목록에서 선택한 글의 원문 저장이 성공하면 등록 완료로 바꾼다. AI 해석 실패는 이 완료 상태를 되돌리지 않는다. 동일 owner/피드 항목 중복 등록은 막지만, 같은 URL의 수정된 본문을 새 버전으로 보관하는 행위를 무조건 중복으로 제거하지 않는다.

### 탐구하기

해석 문서에 핵심 개념, 섹션별 설명, 선행 관계, 예시, 원문 근거, 확인할 질문을 둔다. 원문에 없는 확장은 AI 해석/추가 질문으로 표시한다. 일반 해석은 코드 예제를 의무화하지 않고, 코드 문제는 현재 실행기에서 검증 가능한 내용일 때 별도 요청한다.

실습하기는 세 경로로 나눈다: (1) 해석 자료의 질문에 내 말로 답하고 요약하기, (2) 해석한 개념의 코드 문제를 생성하고 풀기, (3) 기존 기초 구현 카탈로그에서 배우기. 질문·요약은 자동 정답 공개가 아니라 사용자 입력을 먼저 받는 구조다. 기초 카탈로그는 raw 등록을 강제하지 않고 버전이 있는 내장 학습 출처로 취급한다.

다시 검토는 코드/해석/노트의 기한을 한 화면에서 보이게 한다. 기존 코드 복습 간격은 유지하고 일반 자료에는 ‘스스로 설명 가능 / 다시 확인 필요’ 같은 명시적 응답을 받아 다음 일정을 계산하는 안을 권장한다. 단순 페이지 열람을 복습 성공으로 계산하지 않는다. 일반 자료는 추출 적격 확인과 별도로 사용자가 복습 대상으로 선택하는 안을 권장한다. 최초 대상 등록 시점과 일반 자료의 간격은 D2 결정 전 확정하지 않는다. 첫 시각화는 주간 일정+기한 경과 목록이면 충분하며, 측정 근거 없는 개인 망각 확률 곡선을 표시하지 않는다.

### 데이터 쌓기

해석의 ‘정리 확인’ 또는 실습 요약의 ‘검토 완료’가 추출 가능 자료의 입력이 되는 안을 권장한다. 즉시 추출 버튼과 추출 가능 목록은 같은 검토 대상을 연다. 기존 노트의 수동 지식 등록 경로는 유지하며, 새 기능 이용을 위해 AI 해석을 강제하지 않는다.

AI 추출 → 사용자 수정 → 기존 개념 비교 → 근거·관계 검사 → 등록의 순서를 공통화한다. 같은 이름의 개념 자동 병합은 하지 않는다. 현재 note ID에 묶인 proposal을 source kind/ID/version으로 확장하되 기존 note 요청의 호환성을 보존한다. 추출 가능 목록은 원본 데이터에서 조회하고, 후보/보류/등록처럼 지속할 필요가 있는 상태만 저장한다. 모든 이벤트를 담는 새 이벤트 버스는 필요하지 않다.

`action`은 의미가 아직 열려 있다. 추천안은 **실제로 수행한 풀이·설명·실험을 LearningObservation으로 기록**하고, 앞으로 해볼 활동은 응용의 가이드로 두는 것이다. 실행 가능한 절차 자체를 지식 엔티티로 다루려면 입력·출력·전제조건·근거를 가진 별도 모델의 도메인 설계가 필요하다(D3).

### 응용하기 — Deep Inside

제안은 ‘어떤 개념들이 왜 연결되는가 → 내가 답할 질문 → 찾아볼 근거 → 직접 할 작은 실습 → 남길 결과물’로 구성한다. 연결되지 않은 자료가 많다는 사실만으로 관계를 만들어내지 않는다. 근거가 부족하거나 반박/오래된 근거뿐이면 그 한계와 확인 과제를 표시한다.

기존 SQLite 그래프의 제한된 이웃·근거 조회를 먼저 사용한다. 제안마다 사용한 개념·관계·출처 버전을 남기고, 가설적 연결은 확정 관계와 구별한다. 제안 채택은 탐구 기록 저장이며 그래프 자동 등록이 아니다. 완성된 답이나 코드를 선제 생성하기보다 사용자의 설명·비교·실험을 이끄는 안내를 제공한다.

첫 구현 제안은 **사용자 요청으로 한 묶음 생성**이다. 장기 목표인 일정 사이클 생성은 D4에서 주기·앱 종료 중 동작·비용 상한·제안 교체·보관 정책을 정한 뒤 별도 흐름으로 구현한다. 따라서 수동 생성만 완료하고 전체 응용 요구가 끝났다고 표시하지 않는다.

### 설정

GitHub 연동과 공유 기록은 재사용한다. 현재 설정의 저장소 확인은 영속적인 기본 저장소 등록과 다르므로, 사용자별 기본 저장소 하나를 확인 후 저장하는 흐름을 추가한다. 저장소 ID와 표시용 이름을 보관하고, 계정 교체·권한 변경·저장소 이동 후에는 다시 확인한다. 공유 시 대상과 본문을 확인하는 기존 계약은 유지한다. 저장소 등록 자체는 외부 게시를 유발하지 않는다.

AI 설정 초안은 당시 미추적 문서 `docs/deployment-design.md`의 사용자별 키 제안을 참고했다. 후속 구현은 [개인 AI 설정 계획](ai-settings-plan.md)을 따른다. 이는 현재 구현 완료나 승인 증거는 아니다. 사용자당 활성 설정 하나, 허용된 제공자·모델, 서버 암호화 저장, 마스킹된 조회, 키 원문 비반환을 제안한다. 설치된 암호화 라이브러리를 재사용하고 전역 환경변수를 요청마다 바꾸지 않는다.

호출 범위는 자료 해석, 문제 생성/수정, 학습 요약, 노트 후보/인용 보정/대화 검토, 기초 설명 피드백, 향후 Deep Inside, 연결 상태와 사용량이다. 작업은 owner와 설정 버전에 묶는다. 변경·삭제 이후 다음 호출에서 이전 키를 계속 쓰지 않고, 이미 외부로 보낸 요청은 취소됐다고 가정하지 않는다. 로컬 `.env` 설정을 언제 어떻게 전환할지는 D5로 남긴다.

## 7. 이행과 리팩터링

### 데이터 이전 순서

1. 실제 운영 DB를 수정하기 전에 백업/복구 절차와 익명 fixture를 준비한다. AI·runner·새 작업 접수를 정지하는 이행 창을 정하고 버전·행 수·참조 무결성을 기록한다. `scripts/backup.py`와 기존 배포 절차를 우선 재사용한다.
2. 기존 테이블을 지우지 않는 추가형 변경으로 시작한다. 원문은 generation → owner를 추적해 resource에 연결하고, 노트는 기존 ID/버전/이미지와 연결한다. 매핑에 고유 제약을 두어 반복 이행도 중복을 만들지 않는다.
3. 실패한 생성 작업의 원문, 본문을 가져오지 못한 URL, 원문이 이미 없는 옛 context, sample, 내장 카탈로그를 구분한다. 없는 원문을 AI 해석으로 복원했다고 표시하지 않는다. 예전 생성에서만 남은 내용은 실제 저장 상태 그대로 이관한다.
4. 기존 context/set/exercise/attempt/review/knowledge의 ID·날짜·owner·카탈로그 버전·인용 위치를 유지한다. 이미 등록한 노트와 단원은 새 추출 대기 대상으로 중복 등록하지 않는다. 기존 direct-add 근거는 legacy 경로임을 유지한다.
5. 읽기 전환 전에 **기존 삭제 경로부터** 수정한다. context/생성 작업 삭제가 독립 resource를 삭제하지 않도록 보호한다. raw의 영구 삭제는 D1 정책이 결정되기 전 새 기능으로 제공하지 않는다.
6. 새 자료의 쓰기 주체는 하나로 둔다. 호환 API는 새 주체를 호출하게 하고 두 저장소에 무기한 이중 쓰기하지 않는다. 기존 source_documents는 이행 후 호환 조회용으로 남겼다가 소비자가 사라진 별도 변경에서 제거한다.
7. 과거 코드로 되돌릴 때 새 DB를 안전하게 읽는지 확인한다. 호환되지 않으면 쓰기 중단 상태에서 이전 릴리스+백업으로 복구한다. 롤백 시점 이후 작성분 손실 가능성을 명시하고, 백업 복원만으로 무손실이라고 주장하지 않는다.

### 유지보수 경계

- `App.tsx`는 세션·레이아웃·탐색을 중심으로 줄인다. Create/Home/Me의 이동은 해당 기능을 변경할 때 한다. 화면들이 App에서 가져오는 `useApp`, `useResource`, `ErrorNotice`는 실제 호출자를 함께 갱신하는 작은 변경으로 분리한다.
- `backend/service.py`는 현재 인증·학습·생성·실행·관리 동작을 함께 담고 있다. 첫 resource 흐름을 새 도메인 모듈로 두고, 해석 분리 시 관련 생성 코드만 이동한다. 기존 `service.Error/now` 등을 쓰는 모듈과 순환 import를 확인한다. 파일 길이만으로 일괄 분할하지 않는다.
- `ontology.py`의 개념 식별·관계 검증·출처 등록을 공유한다. 노트/해석/실습별로 서로 다른 그래프 저장기를 만들지 않는다. DDL의 분산은 이관 흐름에 맞춰 정리한다.
- 공통 UI는 기존 Select, Markdown, LoadingSkeleton, ReferenceEditor, AnimatedDetails를 사용한다. 전역 CSS 전체 교체·디자인 시스템 재작성은 제외한다.
- 새 도메인의 API/타입/검사는 그 흐름과 함께 변경한다. 기존 api.ts의 모든 타입을 단순 이동시키는 별도 대형 PR은 만들지 않는다.
- 각 흐름 완료 시 README의 사용 경로, 관련 설계 문서, `docs/architecture/journeys.json`의 함수 참조, FS의 관찰 기록을 필요한 범위만 갱신한다. 문서 지도에 없는 동적 호출은 한계로 표시한다.

## 8. 실행 순서와 분리할 작업

추가한 테스트 모듈은 CI 명령에도 포함한다. 실행기/문제 계약 변경에는 기존 `scripts/check-sandbox.py`, 기초 카탈로그 변경에는 `scripts/check-foundations.py`를 추가한다. 브라우저 E2E 실행 스크립트는 frontend/package.json에 없으므로 자동 E2E가 있다고 주장하지 않는다. 필요한 흐름의 재현 절차/fixture를 먼저 준비하고, 반복 검사 필요가 확인되면 그 흐름에 최소 자동화 설정을 포함한다.

수동 확인: 390px/데스크톱에서 다섯 영역 탐색, 저장→해석→실습→추출→그래프→채택, 빈/로딩/실패/재시도, 키보드·포커스·세션 재인증. AI mock 검사는 요청/저장 계약을 확인할 뿐 설명 품질을 증명하지 않으므로, 실제 AI 품질 확인은 별도 예산과 비개인 fixture로 기록한다.

| D4 | Deep Inside의 생성 사이클·비용·미채택 저장 | 수동 한 묶음부터, 이후 주기·상한·대체 정책을 선택 / 처음부터 예약 생성 | P15. 미채택 본문 캐시 수명·중복 억제 메타데이터 보관도 확정 |
| D5 | AI 설정의 기존 `.env`와 사용자 설정 전환 | 사용자 설정을 명시적으로 저장하고, 없을 때 타인/운영자 키로 대체하지 않음 / 로컬 단일 사용자 모드만 기존 환경설정을 표시해 유지 | P12의 호환성·연결 상태, 운영 전환 |

### 2026-10-22 후속 설계 검토 — 추천안 구체화

사용자가 “다음 검토 진행하죠”라고 요청하여 위 항목의 코드 영향을 추가 검토했다. 이는 제품 정책의 선택이나 구현 승인은 아니다. D1 선택 도구는 빈 응답을 반환했으며 어떤 옵션도 선택된 것으로 기록하지 않는다. D1~D5 모두 미확정이다.

**D1 — 보관, 삭제, 지식 철회를 구별한다.**

- 현재 `service.delete_context`는 문제·풀이·생성·원문을 삭제하지만 그래프 스냅샷과 역사 요약은 남긴다. 반면 `reference_notes.archive`는 본문을 보존하면서 그래프 출처를 `deleted`로 바꾸고, 복원해도 `stale`로 둔다. 따라서 두 함수를 이름만 바꿔 통합할 수 없다.
- 추천 의미: 보관은 자료 보관함의 정리이며, 이미 확인한 지식이 틀렸다는 선언과 구별한다. ‘보관하면 그래프의 유효 근거에서도 제외할지’는 D1에서 별도로 확인해야 한다. 첫 버전에 보관만 제공한다는 선택으로 이 정책까지 확정하지 않는다.
- 정상 사례: 글 A를 보관해도 내가 작성한 요약 B의 내용과 출처 버전은 보존된다. 경계 사례: A와 C가 같은 개념을 뒷받침할 때 A 정리가 C의 근거나 공유 개념까지 삭제해서는 안 된다. 영구 삭제를 도입할 때는 `knowledge_sources.body`·인용·이미지·검토 snapshot 등 복제본의 범위도 표시해야 한다. 원문 행 삭제만으로 내용 전체가 사라졌다고 표현하지 않는다.
- 첫 범위 추천은 보관/복원이며, 실제 저장 공간 회수와 완전 삭제는 별도 설계 대상이다. 기존 노트의 그래프 제외 동작을 바꾸려면 해당 호출자와 검사를 함께 변경하는 별도 흐름을 P2 뒤에 명시해야 한다.

**D2 — 추출 적격, 그래프 등록, 복습 예약을 별개로 둔다.**

- 추천 D2a: AI 해석 생성 성공만으로 ‘사람이 검토한 자료’가 되지 않는다. 사용자가 특정 버전의 ‘정리 확인’을 누르면 추출 가능 목록에 나타난다. AI 후보 생성은 별도 요청이며 그래프 등록도 별도 확인이다. 직접 작성한 노트의 기존 수동 등록 통로는 유지한다.
- 추천 D2b: 일반 자료에는 별도 ‘복습에 추가’를 제공한다. 첫 기한은 추가 시점 다음 날, 이후 ‘스스로 설명 가능’이면 3·7·14일, ‘다시 확인 필요’이면 다음 날이라는 단순 간격을 제안한다. 기존 코드 복습은 통과 시 자동 등록하는 현재 계약을 유지한다. 일반 자료 자기평가를 코드 채점 결과와 같은 숙달 점수로 저장하지 않는다.
- 현재 노트 검토는 `reference_notes.answer_review`에서 사용자 답변과 self_explanation 관찰을 먼저 저장하며 AI 실패에도 유지한다. 이 성질을 재사용하되, 답변 저장·AI 피드백 성공·사용자 검토 완료를 동일 이벤트로 취급하지 않는다.
- 정상 사례: 해석 v1 정리 확인 → 추출 가능 목록 표시 → 복습은 아직 없음 → 사용자가 복습 추가. 경계 사례: 확인 중 v2로 바뀌면 v1 확인을 v2에 적용하지 않는다. AI 피드백 실패나 두 번의 완료 요청도 답변·관찰·기한을 중복 생성하지 않는다.

**D3 — ‘행동에 관한 지식’과 ‘내가 한 행동’은 다르다.**

- ‘큐를 사용해 BFS를 구현하는 방법’은 재사용 가능한 절차 지식이고, ‘오늘 BFS 구현을 제출했다’는 개인 학습 관찰이다. 사용자의 action이 어느 쪽인지 아직 확정할 수 없다.
- 첫 추천은 이미 있는 `learning_observations`로 설명·풀이·실험 수행을 연결하고, 절차 설명은 출처와 개념 설명으로 보존하는 것이다. 실행 가능한 절차 노드가 목표라면 이를 미완료 요구로 남기고 별도 입력·전제조건·결과 모델을 설계한다. 관찰만 구현해 action 요구 전체를 완료 처리하지 않는다.
- 검사할 경계: 같은 절차를 두 번 실습하면 관찰은 두 건일 수 있지만 절차 개념을 자동으로 두 개 만들지 않는다. 같은 요청 재전송은 관찰도 중복 생성하지 않는다.

**D4 — 자동 사이클은 비용과 저장 정책을 포함하는 별도 기능이다.**

- 현재 `feeds.poll`은 서버가 실행 중일 때만 주기적으로 돈다. RSS 수집에 쓰는 타이머가 있다고 유료 AI 예약 작업까지 안전하게 처리되는 것은 아니다. `usage.py`는 사용량 기록이며 호출 예산을 강제하는 장치가 아니다.
- 주기안의 비교: 매일은 변화가 적을 때 반복 제안·비용이 늘 수 있고, 매주는 생각하고 실습할 시간을 주며, 그래프 변경만으로 생성하면 작업이 몰릴 수 있다. **명시적으로 켠 주간 사이클 + 변경된 유효 근거가 있을 때 한 묶음 갱신**을 다음 검토용 추천안으로 둔다. 횟수·토큰 상한은 설정 모델과 함께 확정해야 한다.
- 첫 수동 생성(P13)과 채택(P14)으로 제안 품질을 확인한 후 P15를 구현한다. 서버가 꺼졌던 기간의 모든 주기를 몰아서 생성하지 않고 재개 시 최대 한 묶음만 만드는 안을 추천한다. 외부 요청 결과가 불명확하면 무제한 자동 재호출하지 않는다.
- 미채택 제안은 화면 새로고침에도 유지할 수 있는 현재 묶음의 임시 저장으로 취급한다. 교체/만료된 본문을 역사 목록에 누적하지 않는다. 채택된 내용만 독립 탐구 기록으로 보존한다. 임시 보관 기간과 넘긴 항목의 재제안 억제 기간은 아직 미정이다.
- 정상 사례: 변경된 근거로 새 묶음 생성 → 사용자 채택 → 내 탐구에 저장. 경계 사례: 생성 중 근거가 철회되면 새 유효 제안으로 공개하지 않고 다시 확인한다. 갱신 실패 시 이전 묶음은 시각과 유효성 상태를 표시해 보존하며, 채택된 기록은 교체하지 않는다.

**D5 — 현재 단일 소유자 운영을 유지하면서 AI 설정을 전환한다.**

- `backend/access.py`는 현재 단일 소유자 운영 계약이다. 사용자별 키 저장을 이유로 공개 가입·다중 사용자 운영까지 확장하지 않는다. owner별 격리 검사는 다른 자료/키가 섞이지 않는 계약 검사다.
- 추천: 운영은 본인의 저장된 AI 설정을 사용하고, 키가 없거나 실패할 때 공통 키로 대체하지 않는다. 로컬 단일 사용자 모드는 기존 `.env`를 ‘서버 환경설정 사용 중’으로 표시해 명시적으로 유지하는 과도기안을 비교 대상으로 둔다. 저장한 키를 삭제했을 때 환경 키로 조용히 돌아가는 동작은 허용하지 않는 안을 제안한다.
- 키뿐 아니라 실제 사용한 모델도 함께 전달해야 한다. 현재 `usage.start`와 proposal의 모델 기록 역시 `os.environ`을 읽으므로 HTTP 호출 부분만 변경하면 사용량/출처에 잘못된 모델이 남는다. P12 범위에 `usage.py`와 모든 생성 메타데이터 기록을 포함한다.
- 경계 사례: 호출 A 진행 중 키 교체 → 이미 보낸 A는 이전 설정 버전의 결과로 기록 → 다음 호출은 새 버전을 확인한다. 삭제된 키의 후속 호출은 중지하고, 작성한 요약·기존 문제 풀이는 계속 가능해야 한다.

이 검토의 결과는 추천안과 검사 의도의 구체화다. 정책 확정, FS revision 저장, 제품 동작 변경 또는 검증 통과 기록은 아니다.

## 11. FS로 이어갈 때

1. FS 도구의 연결 또는 지원되는 로컬 호출 경로를 확인하고 `get_project_analysis(projectView:true)`로 기준선 준비 상태를 조회한다. 현재 main과 작업 브랜치 차이를 먼저 정리하며 원격 병합 상태를 추측하지 않는다.
2. 환경 → 의존성/계층 → 라우트별 event/state/error/cleanup → 지식 적용 조건 → 발견사항 순서로 전수 분석한다. 기존 역사 분석은 현재 소스 의존성이 맞는 부분만 재사용한다. 분석 범위를 축소하고 전체 완료로 기록하지 않는다.
3. 사용자 의도와 관찰 코드를 분리한 현재 흐름을 저장하고, 실제 접근 가능한 화면을 캡처한다. 미접근 화면과 런타임 미검증은 명시한다. 생성된 project.md·AI 참조·HTML은 도구의 동일 기록에서 만든다.
4. 이 초안의 제안을 proposed flow로 옮기고 화면 scene·상태 소유자·API 경계·정상/실패 시나리오·검사 의도를 연결한다. 관련 learned knowledge를 실제 검색·검토한다. 이번 초안은 그 검색을 수행했다고 주장하지 않는다.
5. 먼저 실행할 흐름에 필요한 D 항목을 확정하고 계획을 저장·검토한다. 장기 미결정 기능은 별도 후속 흐름으로 분리한다. 구현 요청을 받으면 해당 계획에 fs-work를 적용한다.
6. 흐름별로 의미 있는 검사 → 구현 → 필요한 회귀 검사 → 코드/화면 검토 → 범위·안전성 PR 검토를 수행한다. 승인 없이 commit/push/배포하지 않는다. 사용자 요청 범위의 승인과 도구상 기록을 혼동하지 않는다.

이번에 실행하지 않은 것: 제품 테스트·브라우저·실제 AI·DB 이행·배포. 이번 변경은 이 계획 문서뿐이며 FS 정식 분석, 제안 HTML, 실행 계약의 바인딩은 다음 작업으로 남는다.
