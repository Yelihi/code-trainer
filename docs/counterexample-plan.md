# 반례 찾기와 한 줄 디버깅 계획

2026-10-06. 사용자 요청에 따른 계획이며, 이 두 학습 모드는 아직 구현하지 않았다.

## 반례 찾기: 첫 구현 범위

학습자가 틀린 함수를 읽고 오류를 드러내는 입력과 기대 출력을 작성한다. 예: `max(a,b)`가 두 값이 같은 경우를 놓치는 구현을 보고 `a=3,b=3 → 3`을 제시한다. 최소 입력을 요구하는 점수제는 도입하지 않는다.

- 기존 READ/FIX/MODIFY/BUILD 완료 기준과 별개인 선택 연습으로 제공한다.
- JavaScript의 순수 함수, JSON으로 표현 가능한 인자·결과부터 시작한다. 네트워크·파일·임의 패키지와 UI 문제는 제외한다.
- 문제에는 함수 계약, 허용 입력 범위, 틀린 구현을 공개한다. 기준 구현·검증용 반례는 서버에만 둔다.
- 임의 테스트 코드를 받기보다 JSON 인자와 기대 결과를 받는다. 서버가 고정된 호출 코드를 조합하고 입력 크기·깊이·자료형을 검증한다.
- 틀린 구현과 기준 구현을 각각 새로운 격리 실행으로 돌린다. 두 구현이 정상 종료하고, 학습자 기대값이 기준 결과와 같고, 틀린 구현 결과와 다르면 통과한다.
- 컴파일/실행 오류, 시간 초과, 출력 초과는 유효한 반례로 인정하지 않는다. 인프라 장애는 오답으로 기록하지 않는다.
- 기준 결과를 제출 때마다 알려주면 정답 조회 수단이 되므로 실패 시 `입력 범위 밖 / 기대값 재검토 / 두 구현이 같은 결과`까지만 안내한다. 명시적인 해설 열람은 기존 도움 기록으로 남긴다.

## 구현 순서

1. 사람이 검토한 반례 문제 5개(경계값·빈 배열·중복·상태 유지·조건 분기)를 고정 예제로 준비한다. 반환값 직렬화와 입력 계약을 먼저 확정한다.
2. 전용 스키마·저장 테이블과 소유자 권한 검사를 추가한다. 기존 Exercise의 네 단계 enum은 바꾸지 않는다. 문제 버전·runtime digest를 고정한다.
3. 실행기는 기존 브로커의 제한된 실행 API를 재사용한다. FastAPI에 Docker 권한을 추가하지 않는다.
4. 입력/기대 결과 편집, 제출, 힌트·해설, 저장 충돌·중단 후 재개를 연결한다. 원래 코드를 수정하는 FIX와 구분해 “입력으로 오류를 드러내기”라고 설명한다.
5. 고정 문제의 검증 후에만 AI 생성과 연결한다. 이번 개선에서 추가한 `wrong_solutions`는 후보 재료이며, 모든 기존 문제를 바로 반례 문제로 변환하지 않는다. 함수 입력 계약과 결정성 검증이 추가로 필요하다.

## 완료 기준

정상 반례 통과, 실제 정답 구현에 대한 거짓 반례 거부, 틀린 기대값·범위 밖 입력·예외·무한 루프 거부, 공개되지 않은 기준 풀이 유출 방지, 다른 계정 자료 접근 거부, 중복 제출 멱등성, 저장·재접속 복구를 검증한다. 데스크톱·좁은 화면에서 JSON 오류 위치와 제출 결과를 읽을 수 있어야 한다. 효과는 통과율뿐 아니라 새로운 입력에서 스스로 오류를 찾는지로 평가한다.

## 후속: 코드 한 줄 바꾸기 기반 디버깅

`원래 코드 → 한 줄 변경(diff) → 결과/오류 예측 → 실행 확인 → 원인 설명` 순서로 설계한다. 처음에는 `> / >=`, `== / ===`, 변수 범위, 참조/복사, 상태 초기화 위치처럼 단원 안의 차이로 제한한다. 일반적인 정답 코드 작성과 별도로 변경 전후 동작을 비교한다.

예측을 먼저 제출한 후 실행 결과를 보여주고, 실행 후 답안을 바꿨다는 기록도 보존한다. 자유 서술의 AI 평가는 피드백으로만 사용하며, 실행 결과와 일치하는 예측은 결정적으로 채점한다. 반례 찾기의 입력·실행·도움 기록을 재사용할 수 있지만 기능 통합은 첫 모드 검증 뒤 결정한다.
